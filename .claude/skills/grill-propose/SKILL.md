# grill-propose: 質問攻め → OpenSpec proposal

grill-me の「設計ツリーの全分岐を潰すまで詰める」姿勢と、openspec-propose の「change一式を生成する」流れを組み合わせたワークフロー。

**計画のみ**: このワークフローは計画成果物を作るだけ。プロジェクトのコードは編集しない。成果物を出したら止まり、実装は `/opsx:apply` を待つ。

## 質問のルール(全フェーズ共通)

- 質問は **必ず `AskUserQuestion` ツール** で出す。テキストで箇条書きの質問を並べない。
- 1回の呼び出しで **1〜4問**。各問は **2〜4個の選択肢**(「その他」は自動で付くので作らない)。
- `header` は12文字以内の短いラベル(例: 「対象ユーザー」「認証方式」)。
- 推奨案があれば先頭に置き、ラベル末尾に「(推奨)」を付ける。`description` にトレードオフを書く。
- 選択肢を同時に選べる問いは `multiSelect: true`。
- UIレイアウトやデータ構造、コード案の比較には `preview` を使う(単一選択のみ)。
- 回答を受けたら、それによって **新たに生まれた分岐** を次の質問にする。前の回答と矛盾する点があれば指摘して確認する。
- コードや既存specを読めば分かる事実は質問せず、自分で調べる。

## Step 1: 何を作るか把握する

ユーザーの依頼から作りたいものを把握する。まったく入力がなければ、自由回答で「どんな変更を作りたいですか?」と聞く(ここだけはプリセット選択肢なしでよい)。

並行して、読み取り専用で文脈を集める:
- `openspec context --json` でrootを確認し、`openspec/config.yaml` の `context` を読む
- `openspec list --json` と `openspec/specs/` で既存のspec・進行中のchangeを確認
- 関連するコード・ドキュメントがあれば読む

## Step 2: 質問攻め(grillフェーズ)

以下の観点を順に潰していく。該当しない観点は飛ばし、依頼に固有の観点は追加する。

1. **目的・価値**: 誰のどんな課題を解くか、成功の基準は何か
2. **スコープ**: 今回やること / やらないこと、MVPの範囲
3. **ユーザー体験・振る舞い**: 主要フロー、画面や操作、エッジケース・エラー時の挙動
4. **データ**: 扱うデータ、保存先、永続化・整合性
5. **技術選定・設計**: アーキテクチャ、ライブラリ、既存コードとの関係
6. **非機能要件**: 性能、セキュリティ、プライバシー、オフライン対応など
7. **受け入れ基準**: 何ができたら完了か、テスト方法
8. **リスク・未決事項**: 後回しにしてよい判断、依存関係

すべての分岐が解消した(または「後で決める」と明示された)と判断したら、決定事項を短い箇条書きでまとめ、`AskUserQuestion` で確認する:
- 「この内容でproposalを作成する(推奨)」
- 「まだ詰めたい点がある」→ 回答に応じてStep 2を続ける

change名(kebab-case)もこの確認で提示し、必要なら選び直してもらう。

## Step 3: OpenSpec change を生成する

`openspec-propose` スキル(`.claude/skills/openspec-propose/SKILL.md`)の Step 2 以降の手順に従って change を作成し、必要な成果物をすべて生成する。

- grillフェーズで決まった内容を proposal / specs / design / tasks に反映する。
- 「後で決める」とした事項は design.md の Open Questions などに明記する。
- 成果物作成中に新たな重大な曖昧さが出たら、ここでも `AskUserQuestion` で聞く。

## 出力

最後に以下をまとめて止まる:
- change名と場所
- 作成した成果物とその概要
- grillフェーズの主な決定事項と、未決として残した事項
- 「レビューして問題なければ `/opsx:apply` で実装に進めます。」
