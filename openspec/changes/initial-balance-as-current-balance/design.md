# Design

## Context

- 残高は `balanceAsOf`（`src/domain/balance.ts`）で「`account.initialBalance` ＋ 前の暦月までの `balanceDeltas` の合計 ＋ 当月の取引のうち指定日まで」として算出している。`initialBalance` は「最初の残高」で、編集してもその後の全取引の増減が上乗せされる（proposal.md の Why）。
- 口座の編集（`AccountsSection.tsx` の `AccountRow`）は保存済みの `initialBalance` を入力欄に出し、`updateAccount` がそのまま上書きしている。
- `initialBalance` は端末間で同期され、バックアップの検証（`src/domain/backup.ts`）は整数であればよく、負の値も受け付ける。
- 残高調整の取引は `computeAdjustmentAmount` で「実際の残高 − 算出残高」を求めており、今回の逆算も同じ考え方でできる。

## Goals / Non-Goals

**Goals:**
- 口座の編集で入力した額が、保存直後の今日時点の残高と一致する。
- 名前だけの編集で、同期で届いた取引などにより残高がずれないようにする。

**Non-Goals:**
- 「基準日」のような新しいデータ項目を口座に持たせること（データ形式・同期形式は変えない）。
- 過去の月の月末時点の残高を変えずに保つこと。初期残高を変えれば過去の月の表示も同じ差額だけ動く（従来どおり）。
- 残高調整の取引の仕様変更。

## Decisions

### 1. 初期残高を逆算して保存する（データ形式は変えない）

保存する初期残高 = 入力した現在の残高 −（今日時点の算出残高 − 現在の初期残高）。つまり今日までの取引の増減の合計を差し引く。

- 純粋関数 `initialBalanceFor(account, deltas, monthTransactions, date, targetBalance)` を `balance.ts` に追加し、内部で `balanceAsOf` を使う。`computeAdjustmentAmount` と同じ引数の形にそろえる。
- 日付は `todayString()`（端末の日付）。当月の取引は既存の `readMonthTransactions(db, monthOf(today))` で読む（`balanceAsOf` は暦月の増減を前提にしているので、月の開始日の設定とは関係なく暦月で読む）。
- 代替案: 口座に「残高の基準日」を持たせて基準日より前の取引を無視する案は、データ形式と同期・バックアップの変更が必要で、ユーザーが選ばなかった。
- 代替案: 編集時に残高調整の取引を自動で作る案は、取引一覧に意図しない取引が増え、ユーザーが選ばなかった。

### 2. 逆算は `updateAccount` の書き込みトランザクションの中で行う

`updateAccount(id, { name, currentBalance? })` に変え、`currentBalance` が渡されたときだけ `db.accounts`・`db.transactions`・`db.balanceDeltas`・`db.outbox` を含む `rw` トランザクションの中で増減と当月の取引を読み、初期残高を計算して保存する。画面で計算した値を渡す方式にしないのは、画面を開いてから保存するまでに取引が増えても（同期で届いても）、保存時点の取引で逆算できるようにするため。クレジットカードは従来どおり 0 を保存し、`currentBalance` は無視する。

### 3. 「残高を変えなかった」は画面側で判定する

`AccountRow` は編集を始めた時点の今日時点の残高を覚えておき、保存時に入力値がその値と同じなら `currentBalance` を渡さない（初期残高を触らない）。リポジトリ側で「今の算出残高と同じか」を比べる方式にすると、編集中に同期で取引が届いた場合に、名前だけの変更で初期残高が書き換わってしまうため。

### 4. 画面の表示と入力

- 一覧の各行・編集欄の初期値は、既存の `useBalanceAsOf(account.id, todayString())` で読む（行ごとのライブクエリ。口座数は少ないので一括読み込みは作らない）。読み込み中（`undefined`）は一覧では残高を出さず、編集開始は読み込み後の値で入力欄を埋める。
- 編集欄のラベルは「現在の残高」。検証は符号付きの `parseBalance`（`|n| ≤ 999,999,999` の整数）を使い、エラー文言は「現在の残高は整数で入力してください」。登録フォームの「初期残高」（0 以上）は変えない。
- 一覧の表示は「（残高 ¥X）」。見た目は既存の `muted` の注記のままで、`docs/design-principles.md` に照らして新しい装飾は足さない。

## Risks / Trade-offs

- [保存される `initialBalance` が負の値や 999,999,999 を超える値になりうる] → 内部の値であり画面には出さない。バックアップの検証は整数のみなので読み戻せる。登録フォームの 0 以上の制限は入力値だけに掛ける。
- [未来の日付の取引は今日時点の残高に含めないため、保存後のホームの月末時点の残高は入力値と異なることがある] → 仕様のシナリオで「今日時点」を基準と明記した。ホームの当月表示は月末時点のため、未来日付の取引がある場合はその分ずれるのは意図どおり。
- [日付をまたいで編集画面を開いたままにすると、初期値が前日時点の残高になる] → 保存時の逆算は保存時点の今日で行うので、入力値が今日時点の残高になることは保たれる。
- [他の端末で同じ口座の残高を同時に編集すると後勝ちになる] → 既存の同期の後勝ちと同じ扱いで、今回は対処しない。
